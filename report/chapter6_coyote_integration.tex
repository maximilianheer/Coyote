\section{Integration Point}
\label{sec:coyote-integration-point}

The final goal is to place the bitstream checker directly on the Coyote deployment path. In this path, a user bitstream reaches the platform before partial reconfiguration. The checker should inspect the bitstream before it is loaded into the reconfigurable region.

Coyote provides a suitable target because it already separates platform services from user logic. The static shell manages host communication, memory services, networking, command handling, and runtime control. User accelerators are deployed into reconfigurable regions. This structure gives a clear location for inspection before the partial reconfiguration step.

\section{Checker Flow}
\label{sec:checker-flow}

The checker follows the same pipeline used during model evaluation. The incoming partial bitstream is treated as a byte stream. The preprocessing logic resizes the stream into the fixed tensor shape expected by the CNN. The synthesized hls4ml model then produces a maliciousness score or binary prediction.

The deployment logic uses this output to control partial reconfiguration. If the score is below the rejection threshold, the bitstream is allowed to continue to the PR controller. If the score is above the threshold, the platform blocks the reconfiguration and logs the event.

The intended flow is:

\[
    \text{user bitstream}
    \rightarrow
    \text{preprocessing}
    \rightarrow
    \text{CNN checker}
    \rightarrow
    \text{allow or reject}
    \rightarrow
    \text{partial reconfiguration}.
\]

This design keeps inspection inside the FPGA deployment path. It avoids a separate host-side inspection stage and gives the platform a self-contained gate before loading user logic.

\section{Prototype Scope}
\label{sec:coyote-prototype-scope}

This work evaluates the main components needed for such an integration. The preprocessing method is deterministic and simple enough to implement in hardware. The CNN candidates are synthesized with hls4ml and evaluated for latency and resource cost. The final 256$\times$7 candidate is selected as the preferred model for further integration because it has lower latency and much lower BRAM overhead than the 512$\times$7 model.

The current integration is still a proposal and prototype direction. A complete Coyote deployment would require control-plane integration, threshold policy, logging, error handling, and validation with the real PR controller. It would also need a clear policy for low-confidence predictions.

The checker should be used as a defense-in-depth component. It can reject suspicious bitstreams before configuration, but it should operate together with static checks, authentication, and runtime monitoring.
