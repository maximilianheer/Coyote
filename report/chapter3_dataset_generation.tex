\chapter{Dataset and Preprocessing}
\label{ch:dataset-preprocessing}

\section{Dataset Goal}
\label{sec:dataset-goal}

The goal of the dataset is to evaluate malicious-bitstream inspection on the same type of artifact that appears in a serverless FPGA deployment path. The input to the checker is a partial bitstream, not source code, a netlist, or an implementation report. The dataset is therefore built from Coyote-style partial bitstreams~\cite{korolija2020os,ramhorst2025coyote}.

The classification task is binary. Benign samples are partial bitstreams generated from Coyote applications. Malicious samples are partial bitstreams that contain ring-oscillator payloads. Labels are assigned by construction from the generation flow.

This dataset is designed to test deployment-like variation. Samples are generated across different floorplans and configurations so that the classifier is not evaluated on a single fixed placement. The malicious class also includes higher-density RO samples to evaluate how detection changes as the RO footprint increases.

\section{Bitstream Generation}
\label{sec:bitstream-generation}

Benign samples are generated from real Coyote applications. These applications represent normal user accelerators that could be deployed into a reconfigurable region. To increase variation, the applications are built across multiple floorplans and configurations.

The benign catalog contains eight debug-enabled Coyote applications: hello world, HLS vector add, multitenancy AES, user interrupts, perf FPGA, multithreading AES, Euclidean distance, and cosine similarity. It also contains no-debug variants for seven of these applications. In the available manifests, this gives 120 debug-enabled benign samples and 101 no-debug benign samples.

Malicious samples are generated from RO designs from \cite{mahmoud2023practical}. The RO count is varied to create payloads with different footprints~\cite{la2020fpgadefender,provelengios2020power,chaudhuri2023criticality}. This allows the evaluation to distinguish between small low-footprint payloads and larger high-density payloads.

Figure~\ref{fig:dataset-pipeline} shows the dataset generation flow. Both benign and malicious designs pass through a floorplan and configuration sweep before partial-bitstream generation. The output is a labeled dataset of partial bitstreams and metadata.

\section{Dataset Composition}
\label{sec:dataset-composition}

Table~\ref{tab:dataset-composition} summarizes the available generated dataset. The original generated corpus contains benign Coyote bitstreams and normal-RO malicious bitstreams across 15 floorplans, FP00--FP14. The higher-density big-RO extension uses six of those floorplans and is kept separate because it is used for the extended footprint evaluation. Figure~\ref{fig:ro-count-distribution} shows the RO-count distribution for both malicious subsets.

The available generated manifests contain 221 benign samples, 225 normal-RO malicious samples, and 78 big-RO malicious samples. The normal-RO corpus spans 32 RO-count settings. The big-RO extension spans 13 higher-density RO-count settings. These counts are not full Cartesian products. For normal RO, we did not build every RO setting on every floorplan. Instead, the generation flow used more RO-count settings and a subset of floorplan combinations to keep the malicious sample count close to the benign count. For benign samples, the intended catalog is 15 variants across 15 floorplans, but some builds did not finish, leaving 221 available benign bitstreams.

Each sample also stores metadata used during analysis. This includes the design source, floorplan, configuration, label, bitstream size, and estimated RO footprint when applicable. The RO footprint metadata is used later to evaluate whether misses concentrate in small malicious designs.

\section{Preprocessing}
\label{sec:preprocessing}

The preprocessing step converts each partial bitstream into the fixed input shape expected by the CNN. Related work has used bitstream-derived tensors or image-like transforms for FPGA classification tasks~\cite{rettkowski2019inspection,chaudhuri2022detection,chen2020bitstreamimage}. Our transform treats the entire \texttt{.bin} file as a byte stream. It does not skip headers, reverse-engineer the bitstream, or extract hand-crafted circuit features.

\begin{algorithm}[t]
    \caption{Pseudocode for deterministic byte-image preprocessing.}
    \label{alg:byte-preprocessing}
    \begin{algorithmic}[1]
        \Require bitstream path $p$, image height $H$, image width $W$
        \State $T \gets H \cdot W$
        \State $b \gets \Call{ReadAllBytesAsUint8}{p}$
        \If{$|b| > T$}
            \State $i \gets \lfloor \Call{Linspace}{0, |b|-1, T} \rfloor$
            \State $w \gets b[i]$
        \Else
            \State $w \gets \Call{ZerosUint8}{T}$
            \State $w[0:|b|] \gets b$
        \EndIf
        \State $w \gets 255 - w$
        \State $x \gets \Call{Reshape}{w, H, W, 1}$
        \State $x \gets x / 255.0$
        \State \Return $x$
    \end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:byte-preprocessing} is the exact preprocessing rule. Long bitstreams are sampled uniformly across the full byte range using deterministic \texttt{linspace} indices, rather than truncated. Short bitstreams are padded with raw zero bytes before inversion, so padding becomes normalized value 1.0 after division by 255. The rule is deterministic at every resolution, although each resolution has its own target length and sampling grid.

The main input resolutions are
\[
    128^2,\quad 256^2,\quad 512^2.
\]
Larger resolutions are also used during model exploration to measure how much classification quality improves when more bitstream detail is preserved.

This representation is useful for two reasons. First, it gives CNNs a fixed-size input while preserving byte-level structure from across the bitstream. Second, the operation maps directly to FPGA logic before inference. We wrote this preprocessing block as HLS C++ raw-byte downsampling logic, lowered it to Verilog through the HLS flow, and used it in the deployment-oriented latency results reported in Chapter~\ref{ch:hls4ml-results}. This matters because the final goal is an FPGA-resident checker that can run in the deployment path.

\section{Dataset Limitations}
\label{sec:dataset-limitations}

The dataset supports a feasibility study. It does not cover every malicious FPGA design. The malicious class focuses on RO-based payloads, and labels are assigned by construction. This means the classifier may learn artifacts that correlate with maliciousness, such as payload size, routing density, or floorplan effects.

The extended RO-footprint evaluation helps address this issue by showing where the detector is strong and where it is weak. Small RO payloads remain the harder case. Larger RO payloads are more relevant for power-stress attacks and are evaluated separately in Section~\ref{ch:cnn-pipeline}.
